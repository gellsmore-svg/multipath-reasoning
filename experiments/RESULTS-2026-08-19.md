# First recorded comparison — 2026-08-19

Seven records, four oracle tasks, one model. **No significance is claimed and none
can be.** This is the first data in this directory; before it, every claim in the
repository rested on design argument alone.

## Headline

On four real debugging tasks with an objective oracle, **a single tool-using
trajectory matched ground truth on all four**, blind-graded. On the one task where a
population was also run, it matched too — at **4.9× the tokens and 5× the
invocations** for the same graded outcome.

For this task family, the population bought no measurable accuracy.

## Tasks

Each task is a real bug-fix commit from a production repository in the same estate.
The snapshot is `git archive` of the fix commit's **parent**, so the fix is
unreachable: no `.git`, verified no answer text in the tree, and no contaminating
installed dependency. The symptom given to the model is the reporter's half of the
commit message; the cause is withheld and used only for grading.

| Task | Fix commit | Symptom given |
|------|-----------|----------------|
| `hoglah-segv` | `bda0802` | intermittent exit 139 mid-suite, no traceback |
| `mahalath-witness-race` | `90a2ea3` | trace events silently dropped under concurrency |
| `milcah-queue-path` | `4f36420` | specialist calls block to a 240s timeout |
| `milcah-submitter-attr` | `356f8ce` | every call `blocked`, zero model calls, tests pass |

All four were selected because the *original engineer's* first hypothesis was wrong —
the `hoglah-segv` commit message records that the crash was "first assumed" to be at
interpreter shutdown.

**That selection criterion did not transfer.** What was hard for a human under time
pressure was not hard here. Every task was solved by one careful pass, and in most
cases the model went further than the original fix: four independent paths built
standalone reproducers and *measured* the crash rate (2/20, 3/10, 31/60, 34/40;
0/20–0/60 with the lock taken), against the commit's own "2 in 8 before, 0 in 14
after".

## What the recursive arms did — and did not — test

**The falsification criterion in `experiments.md` was not fully exercised.** It
requires compute-matched single-path to match *recursive* Multipath **and** the
full-state-leak ablation to match recursive. Neither recursive nor the leak ablation
ran, for a reason worth recording:

`state_0` on `hoglah-segv` came back with `distinct_solutions: 1` across five
independent paths and zero material disagreement on the cause. That is
`DEGENERATE_POPULATION`, and the method's own rule
(`references/failure-modes.md`) says not to spawn G1 — later generations cannot
decorrelate what G0 did not. **The method declined to run its own recursive stage,
correctly**, and stopped at 5 invocations instead of 15.

That is a real point in its favour, and an unexpected one: the cheapest honest
outcome was reached by a diagnostic that only exists because of the review in
issues #7–#23. It also means the leak ablation — the sharpest test in the design —
remains untested, because a task this easy cannot exercise it.

## The one signal that was not a tie

Accuracy was 7/7. Calibration was not.

The two arms that spent the *most* compute on a single trajectory produced the
confident errors. `single-path-compute-matched` — explicitly told to enumerate ≥4
candidates and self-critique twice — asserted the race was "provably guaranteed" on
an argument it never established, and shipped no uncertainty section at all. Plain
`single-path` and `multipath-g0` each had zero notable errors and flagged the genuine
residual uncertainty (which of two teardown windows fires).

`multipath-g0` preserved that uncertainty because `forbidden_collapses` obliged it
to. That is the machinery doing what it claims — on n=1, judged by one grader.

This is the honest shape of the result: on this family, the population did not buy
accuracy, and may have bought calibration. One task is not evidence for the second
half of that sentence.

## Second run: does the population or the parent do the work?

The first run could not answer this, because the frontier model never produced a
wrong population to aggregate. A small local model does, immediately.

**Setup.** The same `close()`-without-the-lock bug, reduced to a bounded code snippet
(no agentic tool use, so this isolates reasoning aggregation from tool-use ability).
Paths are `gemma4:e2b` (7.2 GB) at temperature 0.8. Four populations of N=5 were
formed from independent samples:

| Population | Path culprits | Majority vote | Correct? |
|---|---|---|---|
| `fc1` | `mark_result_published` ×5 | `mark_result_published` | ✗ |
| `fc2` | `mark_result_published` ×5 | `mark_result_published` | ✗ |
| `dc1` | `close` ×4, other ×1 | `close` | ✓ |
| `dc2` | `close` ×4, other ×1 | `close` | ✓ |

The `fc` populations are the case `README.md` describes and no prior run produced: a
population that is **unanimous and wrong**. Majority vote crowns
`mark_result_published`, which the code shows holding `self._lock`.

**Two arms, identical prompt, differing only in the parent.** Both were given the
source code, the five path answers, and the convergence rule — *prefer a claim the
source supports over one that is merely popular*.

| Population | Majority | Arm A parent (`gemma4:e2b`) | Arm B parent (Claude) |
|---|---|---|---|
| `fc1` | `mark_result_published` | `mark_result_published` | **`close`** |
| `fc2` | `mark_result_published` | `mark_result_published` | **`close`** |
| `dc1` | `close` | `close` | `close` |
| `dc2` | `close` | `close` | `close` |

```
arm A == majority vote : 4/4        arm A correct : 2/4
majority correct       : 2/4        arm B correct : 4/4
```

### The finding

**The weak parent reproduced the population's mode in 4 of 4 cases.** It added no
information over taking the majority. On both false-consensus populations it returned
the wrong culprit and marked it `STABLE_HIGH_CONFIDENCE` — it did not merely fail to
detect the false consensus, it certified it. On `fc2` it recorded
`SUPPORT: reconstructed` for a claim resting on nothing but agreement; on `fc1` it
emitted prose where the enum belongs. The support taxonomy, which is the method's
central distinction, was filled in wrongly while remaining schema-valid.

**The frontier parent was right 4 of 4, including where no path was.** `close` appears
in **zero** of the five `fc` path answers, so arm B cannot have aggregated its way to
it. It read the code and overrode the population. Its own reasoning says so: *"All
five paths blame `mark_result_published`, but the code shows it holding `self._lock`."*

Both halves point the same way:

> The convergence rule is inert without a parent that can independently verify against
> the source. Given a capable parent, the population was not merely unnecessary — it
> supplied a wrong prior that had to be defeated. Given a weak parent, Multipath
> degenerates exactly into the majority vote it was built to replace, and launders the
> result as high confidence.

This is the review's open question #1 (`docs/technical-description.md` §Actors;
issue #7) answered with data rather than argument: **the ceiling is the parent's
discrimination, not N.**

### Caveat

Four populations, one task, one model pair. The 4/4 arm-A-equals-majority
correspondence is striking but small, and both regimes come from the same underlying
bug. What makes it worth recording is that the mechanism is legible — arm B states in
its own output why it rejected the majority — not that the sample is large.

## Third run: heterogeneous population, peer convergence, no privileged parent

Runs 1 and 2 both failed for the same reason: whenever the aggregator was a frontier
model, it could solve the problem alone, so the population's contribution was
unmeasurable. This run removes every large model from the loop.

### Why resampling could not have worked

Monte Carlo, bagging and ensemble forecasting reduce **variance** on errors that are
independent and roughly zero-mean. Temperature sampling perturbs the *draw*, not the
*model*: same weights, same prior, same pull toward the same wrong framing. The errors
are correlated **and** biased, so averaging converges to the bias rather than cancelling
it. Measured: `gemma4:e2b` produced `mark_result_published` on **17 of 17** samples and
never once produced the correct answer. More samples make that worse, not better.

Multipath as originally specified is a variance-reduction method aimed at a bias problem.

### The pipeline that does work

Four local models — `gemma2:2b`, `gemma4:e2b`, `gemma4:latest`, `mistral-small` — spanning
1.6 GB to 14.3 GB and two families. No frontier model at any stage.

**Stage 0 — derive the rule.** Each model is shown the class and asked what convention
its methods follow, and how it would audit for a violation. The prompt never says *lock*,
never says *close*, and explicitly forbids diagnosing. **All 8 samples derived the
lock-discipline invariant unaided**, with mechanically applicable checks, e.g.

> *Ensure every method contains a `with self._lock:` block around any database operations
> involving `_conn`.* — mistral-small

**Stage 1 — generate.** 4 models × 4 samples = 16 candidates.

```
mark_result_published 10 · close 3 · publish_now 2 · claim_for_processing 1
MAJORITY VOTE -> mark_result_published   WRONG
```

**Stage 2 — verify.** The same four models each judge a **deduplicated** candidate list
with all vote counts stripped, against the derived rule. They cannot count, only check.

| Rule used | Consensus | Correct |
|---|---|---|
| experimenter-written | `close` 3/4 | ✅ |
| **model-derived (verbatim from Stage 0)** | **`close` 3/4** | ✅ |

Supplying the rule bought nothing. The pipeline is self-contained: symptom in, correct
answer out, nothing above 14.3 GB.

### The mechanism

`gemma4:e2b` generated `mark_result_published` on every one of 17 samples and never
produced `close`. Asked to *verify* a candidate list, it selected `close` correctly.
Same model, same code, same context window.

**Generation is the hard step; verification is not.** That splits the work cleanly:

| step | small models? |
|---|---|
| derive the audit rule | yes — 8/8, including 1.6 GB |
| verify a candidate against it | yes at ≥ 7.2 GB |
| generate the answer unaided | **no** — 0/17 |

The population's job is therefore **coverage, not insight**: heterogeneity exists to get
the right candidate onto the list at all. `close` entered the pool only from `mistral-small`
and `gemma4:latest` — a different family fails differently, which is the decorrelation
temperature sampling cannot provide. Then verification, which every capable member can do,
picks it out. `close` was 3 of 16 in the pool; voting buried it; verification surfaced it.

This is the first evidence in this repository that the method's central claim —
*prefer source-supported over popular* — beats majority vote in a setting where no single
participant could have produced the answer alone.

### Limits

- One task, one bug, one run per configuration. No rate is established.
- `gemma2:2b` (1.6 GB) dissented in both verification runs, hallucinating that `close()`
  does not touch `self._conn`. It derived the rule correctly but cannot apply it. The
  comprehension floor for participation sits between 1.6 and 7.2 GB, and a peer below it
  contributes confident noise, not diversity.
- `gemma4:latest` reached `close` by reasoning but emitted `Candidate:` instead of
  `CULPRIT:` and was truncated; it was scored by a format-tolerant parser. Three separate
  measurements in this session were initially distorted by token-budget and parser
  artifacts, each time in the direction that flattered the conclusion being drawn.
- The candidate set was deduplicated by the harness, not by a model. Automating that step
  is untested.

## Scope — what this does not show

- **One domain.** Single-root-cause debugging with full source access and an
  objective oracle. The method's stated targets also include research synthesis,
  architecture, and decision analysis, where no oracle exists. Nothing here speaks to
  those, and the `STABLE_WITH_UNCERTAINTY` success criterion was never exercised.
- **One model.** All paths were the same model at the same settings, so
  `error_correlation_risk: "high"` throughout. The mixed-model condition is untested.
- **Four tasks.** No statistical claim is made or available.
- **A grader that is also a language model,** applying pre-registered elements. It
  found real errors in three answers, so it was not merely rubber-stamping, but it is
  not an independent oracle.
- **Selection.** Tasks were chosen before any condition was run, on a criterion
  (the original engineer guessed wrong) that turned out not to predict difficulty
  here. No task was dropped after seeing results.

## What would actually test this

The bottleneck is task difficulty, not experimental design. A discriminating task
needs a cause that a careful single read does not surface — genuinely distributed
across components, or under-determined by the available evidence. Mining bug-fix
commits did not produce one in four attempts.

Until such tasks exist, the defensible claim is narrow:

> On single-root-cause debugging tasks with an oracle and full source access, one
> tool-using trajectory is sufficient, and Multipath's cost is not repaid in accuracy.
> Its own degenerate-population diagnostic correctly detects this and stops early.

## A gap this run exposed

`conserved_findings[].support` has no value meaning **verified by execution**. Four
paths independently reproduced the segfault and measured it — stronger evidence than
either `source` or `reconstructed` — and the enum cannot express it. It was recorded
as `source` with the distortion noted. Worth a `verified` value, or an explicit
`verification: {artifact, result}` field.

## Reproducing

Raw path files, `state.json`, projected views, and grader verdicts are in the run
tree referenced by each record's `artifact_dir`. The `state_0` for `hoglah-segv`
validates clean under:

```bash
python3 skill/scripts/validate_state.py state.json --source source.md --run-dir gen-0
```

It did not validate on the first attempt: `verified_stable_claims` held paraphrases
rather than exact `conserved_findings` claim strings, and the support↔stability
binding added for issue #18 rejected it. That check earned its place on live data.
